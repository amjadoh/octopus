# بنية الأخطبوط 0.2.0

مشروع واحد ينتج نسختين باستخدام Android product flavors. `diagnostic` يستخدم الخدمة التشخيصية والبيانات المحلية الحقيقية فقط؛ `demo` يضيف رحلة Compose محلية ببيانات توضيحية تحت `src/demo` حصريًا. لكل نسخة حزمة وواجهة تشغيل منفصلتان؛ خدمة الإتاحة معطلة في بيان نسخة العرض. لا تُستخدم WebView للصفحات الأصلية.

`DemoJourneyController` يدير حالات الطلب وخياراته ونتائجه التجريبية، دون Context أو Intent أو الوصول إلى خدمة الإتاحة. `DemoPricing` يحسب المثال بالهللات الصحيحة. تحفظ ViewModel الحالة خلال تغيير حجم نافذة الهاتف ودوران الشاشة؛ لا تُعد هذه الآلية حفظًا مضمونًا بعد إنهاء عملية التطبيق.

تستخدم النسختان `OctopusPalette` للأبيض والبترولي؛ لا يوجد تبديل ألوان يعيد التصميم السابق. المحولات الحقيقية لا تستورد كتالوج العرض أو أسعاره.

`ui`: صفحات Compose وإفصاح الخدمة والتصدير والحذف.

`data`: Room لتقارير غير حساسة وDataStore للموافقة والمنصات المسموح بها.

`domain`: أنواع المبالغ والسلال والنتائج المتحقق منها؛ النتيجة التشخيصية ليست VerifiedQuote.

`automation`: خدمة قراءة فقط، جلسة صريحة واحدة 90 ثانية، تحقق من حزمة النافذة النشطة، واستخراج لحظي لا يحفظ النص الخام. تتوقف عند قفل الجهاز أو مغادرة التطبيق بعد رؤيته أو تغيير الإعدادات أو التخطيط.

`providers`: محول تشخيصي مستقل لكل منصة، بمستوى تحقق صريح غير مختبر على الجهاز.

`pricing`: تحويل دقيق إلى هللات، واستخراج محافظ للصفوف المعروفة. محرك المقارنة لا يقبل إلا قيمًا متحققًا من السلة والعنوان والفرع وشمول الرسوم وحداثة القراءة، ولا يُستخدم لتصنيف نتائج التشخيص.

`safety`: سياسة قراءة تتطلب كل الشروط، ومنع جميع أنواع إجراءات التحكم. لا يوجد منفذ Android تفاعلي في إصدار المرحلة الأولى.

`diagnostics`: تصدير JSON محدود وموسوم صراحة بأن النتائج ليست أسعارًا نهائية.

التوسعة اللاحقة: ScreenRecognizer يعتمد على شاشات فعلية، وAutomationOrchestrator وحالاته وCartReconciler ومحرك مطابقة وقراءة عنوان/أصناف. تُبنى بعد فحص الجهاز، ولا تُستبدل هنا بتنفيذ شكلي.
